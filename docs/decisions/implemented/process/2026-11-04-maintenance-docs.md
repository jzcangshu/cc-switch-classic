# Agent Note: 维护文档按阶段公开、私人运维单独保存

Status: implemented（已实施）

## Problem（问题）

原维护长文同时承担产品契约、测试经验、发布操作和记忆索引；助手入口与更详细的裁决手册被忽略规则挡在仓库外。新贡献者无法取得完整规则，维护者又容易在长文中漏掉当前步骤。旧资料还包含过时基线、五语言口径和“单跑通过即可排除回归”的判断，直接拼接会扩大冲突。

## Decision（决定）

根目录统一入口按接手、实施、专项任务、审查、发布分阶段路由；维护入口保留导航，各规则只在其领域文档维护。兼容助手文件只跳转统一入口，并由检查器防止另起一套规则。公开决策放在本目录，使贡献者不依赖私人助手记忆。

个人路径、服务器、账号、代理、签名材料位置和瞬时工作区状态留在仓库外私人目录。原交接、本地裁决手册和操作备忘保留原件与来源摘要；公开资料只吸收独特且仍有效的规则。用户手册、历史发布说明及正在使用的截图资源保持原引用位置。

审查材料生成工具固定四个提交和视觉参照，要求当前候选已提交、工作区干净，输出三组差异和未审查模板。自动化不替代语义、实际渲染或原生平台验证。文档检查及工具测试进入持续集成，检查入口、链接、公开范围和关键拒绝路径。

旧维护文档中“不上传助手文件”和“只追加单篇记忆”的规则由本决定取代；私人手册中的五语言口径按既有四语言产品裁决纠正。普通协作采用正常主分支历史，避免整树镜像覆盖远端修改；独立发布历史的迁移仍须审查最终内容。

## Alternatives considered（考虑过的方案）

1. **继续单篇维护长文**：全文检索与复制最简单，也不需要迁移链接；但读者每个阶段必须自行筛选，私人执行细节与公共契约容易混在一起，无法满足贡献者分阶段接手。
2. **为每个助手维护完整规范副本**：各工具可直接读取熟悉文件，启动最方便；但多份裁决和发布清单会漂移，恰好重现本次发现的语言与版本冲突。
3. **只发布脱敏交接、继续依赖私人全局工作流**：迁移成本小，也可复用维护者已有工具；但贡献者无法复现，交接中的瞬时状态仍会伪装成长期事实。

## Consequences（后果）

贡献者能通过同一入口定位本阶段需要的全部规则，私人执行条件不再成为协作门槛。代价是新增少量文档与两个维护工具，需要在规则变更时同步导航和对应检查。检查器只能发现明确模式，仍需人工审查敏感信息和语义；审查生成工具拒绝已有输出目录以避免覆盖，旧输出由维护者自行管理。

本次不改产品代码、不推进尚未合并的内核更新，也不改写公开历史。若未来维护规范数量继续增长，优先缩短和合并重复规则，再考虑增加路由层级；不以新增目录代替清晰归属。

## Testing（验证）

文档检查覆盖统一入口、兼容入口、链接与公开文件范围；维护工具测试覆盖无效引用、基线方向、脏工作区、目录越界、已有输出保护及三组完整差异。手工对照原维护文档各节、裁决手册与交接修复，确认独特规则有归属，瞬时状态没有变成永久规范。

实际命令结果与提交范围随本次交付记录提供；产品行为未改动，不把产品全量测试当成这次文档迁移的必要证明。
