# Agent Note: 维护规则按阶段组织，详细契约按模块公开

Status: implemented（已实施）

## Problem（问题）

贡献者需要在接手、实施、审查和发布时取得完整且适用的规则。入口过长会淹没当前步骤，过度概括又会丢失裁决标准、原生字段语义和验收条件。私人运维信息还需要独立的访问边界。

## Decision（决定）

[统一入口](../../../../AGENTS.md) 按任务阶段路由。维护入口负责导航，项目契约定义产品边界，裁决手册定义是否和如何接入，上游同步定义执行步骤，质量审查定义验收。已有详细手册按模块复用和打磨，规则在唯一归属处完整维护，其余使用链接；兼容助手文件只跳转统一入口。

私人运维文档保存在仓库外，仅作者可访问。公开维护入口写明作者授权的精确定位路径与访问说明，文件内容、服务器、账号和其他个人目录不入库。检查器只对该文件中的精确路径引用放行，路径变体和其他文件仍受检查。

材料生成工具固定官方前后、经典版前后提交与视觉参照，生成三组完整差异、裁决路径表和未审查报告。实施前后均可使用，工具不代替裁决、真实渲染与原生验证。文档检查验证公开范围、链接和入口可达，工具测试覆盖关键拒绝路径及报告内容。

## Alternatives considered（考虑过的方案）

1. **单篇完整手册**：检索方便，但不同阶段加载成本大，模块细节难维护，私人信息容易混入。
2. **只保留简短总规范**：容易阅读，但缺少可执行判断与验收，开发者仍需寻找私人记忆。
3. **按阶段导航并保留模块手册**：兼顾完整性与按需阅读，代价是维护跨文档链接和明确归属；采用此方案。

## Consequences（收益与代价）

贡献者可独立执行完整同步和审查，作者可从公开入口定位私人文档。细节和导航分离降低重复，但每次规则变化都需检查相关引用、模块契约和公开边界。原始交接与一次性材料保存在仓库外，不成为协作前提。

## Testing（验证）

运行 pnpm docs:check（文档检查）、pnpm test:maintenance（维护工具测试）和 git diff --check（差异空白检查）；人工检查阅读路线、规则冲突、公开内容及暂存范围。该验证不宣称产品内核、图形界面或原生平台已经通过验收。
