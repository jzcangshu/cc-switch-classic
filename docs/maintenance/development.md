# 开发与验证

修改代码、运行测试前阅读。产品约束见 [项目契约](project-contract.md)，审查判定见 [质量审查](review.md)。

## 环境与源码地图

工具版本读取 .node-version（节点运行时版本文件）、package.json（依赖及命令清单）的 packageManager（包管理器版本字段）和 rust-toolchain.toml（后端工具链配置）；持续集成还可能覆盖其他运行时版本，不能把维护者本机版本写成项目硬要求。安装依赖使用锁文件，不顺手重写锁文件。

| 所属目录                                                              | 职责与审查边界                                                                   |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| src/components（前端组件）                                            | 供应商、设置、账号、用量、会话等业务界面；通用视觉组件只放可复用的展示与交互能力 |
| src/lib/api（后端接口封装）、src/lib/query（查询状态）                | 命令契约、缓存键、刷新与失效；不能靠界面兜底掩盖状态模型错误                     |
| src-tauri/src/commands（命令入口）、services（业务服务）              | 输入边界与业务编排；新增命令须同时注册、封装并验证调用链                         |
| src-tauri/src/proxy（本地代理）                                       | 协议转换、路由、流式传输、额度和认证边界                                         |
| src-tauri/src/database（数据库）、配置模块                            | 迁移、默认值、原子写入、旧配置及未知字段保留                                     |
| src-tauri/src/session_manager（会话管理）                             | 原生会话发现、读取与恢复；用量导入还需核对业务服务中的导入器                     |
| tests（前端测试）、后端单元及集成测试                                 | 以行为和数据契约为主；测试替身要保留被验证的关键边界                             |
| src/whats-new（更新摘要）、.github（协作自动化）、scripts（工具脚本） | 发布口径、持续集成与维护工具，各自有独立验证要求                                 |

进入模块后继续查其实际调用方和相关测试；目录地图不会列举每个新应用，不能拿遗漏当作不支持该应用的依据。

## 用户数据隔离：先完成再运行

1. 找到被测代码的配置、数据库、账号和会话目录解析逻辑。为本轮测试建立空的独立临时目录，设置 CC_SWITCH_TEST_HOME（测试用户目录覆盖变量），检查应用专属目录覆盖变量和设置夹具是否也隔离。
2. 核对旧 HOME（用户目录环境变量）兼容回退不会到达真实配置。现有代码有测试覆盖优先路径，合并时必须保留；仅清除 HOME（用户目录环境变量）不能证明所有路径安全。需要清除时只在测试子进程中处理并保留原值。
3. 更改进程环境变量的测试必须串行或使用项目现有共享锁，并在失败路径恢复；独立运行通过不能排除整套运行时的状态泄漏。
4. 代理与接管测试使用隔离端口和测试配置。端口已被桌面应用占用时选择可隔离的方案或说明阻塞，不擅自结束用户进程。
5. 构建目录通过 CARGO_TARGET_DIR（后端构建输出变量）选择空间充足的本地磁盘；具体盘符属于私人资料。低内存环境可降低并发、关闭增量编译，但需记录实际参数，不能用资源限制解释一切失败。

## 基础命令

以下命令从仓库根运行；后端命令先完成上面的隔离。包管理器命令与项目脚本保持一致：

```sh
pnpm install --frozen-lockfile
pnpm docs:check
pnpm test:maintenance
pnpm typecheck
pnpm format:check
pnpm test:unit --maxWorkers=2 --minWorkers=2
pnpm build:renderer
cargo fmt --check --manifest-path src-tauri/Cargo.toml
cargo clippy --locked --manifest-path src-tauri/Cargo.toml -- -D warnings
cargo test --locked --all-targets --manifest-path src-tauri/Cargo.toml -j2
```

其中两工作进程和两个编译任务是资源受限时的保守参数，不是产品逻辑。持续集成使用的后端测试运行器以工作流为准；本地全目标测试与远端运行结果一起作为证据。前端格式脚本仅覆盖源码，新增维护工具由专门命令检查。

纯文档改动运行文档检查、查看差异与隐私检查即可；维护脚本变化还须运行其测试。改变依赖、运行时或构建链时必须补构建验证。涉及前后端的内核同步要执行完整基础检查，并跟踪相应平台的远端检查。不存在依赖的阶段可按审查指引记录不适用。

## 失败归因

失败时保留最初命令、提交编号、平台、退出码和完整日志。先整文件复现，再区分产品缺陷、测试隔离、导入期平台判断、资源不足和工具链问题；必要时复现原并发条件。重跑通过只是一条证据，不能自动消除最初失败。

特别注意模块初始化时计算的常量：替换后续函数调用不一定能影响已求值常量。跨平台窗口行为必须检查平台初始化路径，不能直接删除测试断言或无限提高超时来变绿。

截图必须覆盖真实尺寸计算、长文本与临界宽度。浏览器预览可以辅助前端检查，但窗口拖动、系统托盘、原生对话框与更新安装仍要在桌面环境验证。
