# 推送与发布

推送代码和发布版本是不同动作；只执行当前任务授权的部分。开始前重读对应步骤，不能凭上次经验跳过清单。

## 1. 推送代码

1. 读取 [质量审查](review.md)，确认适用门禁、隐私检查和审查结论。查看工作区及暂存差异，明确本次只包含哪些文件。
2. 通过远端地址确认目标是本项目。获取目标主分支，比较自任务起点以来的**全部变化**，特别是网页端直接修改的主页和文档；不能只通过提交标题判断。
3. 在本项目主分支历史上工作时，正常合并或变基远端新增改动，处理冲突后复验，再进行快进推送。贡献者走合并请求；维护者得到授权时可直接推送主分支。
4. 如果内核开发分支携带上游历史，而发布库采用独立历史，先在发布库主分支上制作可审查的应用结果，逐项保留远端改动。旧版整树镜像是历史运维方案，不是默认命令；不得直接把候选树嫁接到远端父提交而跳过内容合并。
5. 推送后核对远端提交编号和持续集成作业确实对应本次提交。权限、网络或竞争性更新阻止推送时保留提交，说明阻塞；不强制覆盖。

文档门禁工作流会检查文档和维护工具；产品工作流按路径决定运行前后端检查。开发分支单独推送不一定触发产品检查，合并请求或主分支结果才是对应证据。不要把“跳过”写成“通过”。

## 2. 双版本口径

| 用途           | 真值位置                                                                                                | 规则                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 经典版产品版本 | src/lib/classicVersion.ts（前端常量）与 src-tauri/src/commands/misc.rs（后端常量）                      | 两处必须同值；发布标签、关于页、更新比较与发布链接使用此版本 |
| 官方内核版本   | package.json（应用依赖清单）、src-tauri/Cargo.toml（后端包清单）、src-tauri/tauri.conf.json（桌面配置） | 跟随实际已集成内核；同时核对后端锁文件中的本包版本           |
| 产品发版增量   | 本次实际发布内容                                                                                        | 跟进内核才升次版本；未跟内核一律升补丁版本，即使包含新功能   |

读取桌面应用版本的通用接口返回的是内核版本，不能拿它拼产品发布标签。对外展示同时清楚区分产品与内核；主页徽标及正文不能各写一份互相矛盾的“当前版本”。

## 3. 打标签前逐项核对

- [ ] 已明确本次发版授权、目标提交与经典版版本；内核同步的完整审查记录已完成。
- [ ] 前端与后端两处产品常量同步；执行读取真实生产常量的守卫测试，不新增测试专用副本。
- [ ] 内核版本确实对应已集成代码；相关清单与锁文件一致。
- [ ] 按 [更新摘要说明](../../src/whats-new/README.md) 创建经典版版本文件，四语言完整，仅描述实际已发布的变化。
- [ ] 更新主页版本徽标及正文中的版本信息；大范围变化补产品发布说明，保留历史上游发布说明的来源身份。
- [ ] 应用内发布链接使用经典版版本，可用更新链接使用目标更新版本；核对指向本项目。
- [ ] 获取远端主分支并复核内容，推送已验证提交；确认标签指向相同提交，再创建 v{产品版本}（产品版本标签）。

## 4. 更新与签名边界

检查更新和安装更新必须按相同的经典版口径比较。验证目标版本低于、等于、高于本地版本时的行为；不得因内核版本较大而漏掉产品更新，也不得因两处常量不同造成同版重装循环。

src-tauri/tauri.conf.json（桌面配置）的更新地址指向本项目；安装器中的 version_comparator（自定义版本比较器）保留。签名私钥只在受控本地存储和发布平台的秘密变量中使用，不在源码、日志或报告展示；工具需要密钥正文时注入其内容，不能把本地路径误当密钥内容。

## 5. 发布产物验收

- 正式发布不得标为预发布，否则产品采用的最新正式版入口不会指向该版本。
- Windows（微软桌面系统）提供两种架构的 NSIS（安装器）和便携压缩包；不回退 MSI（系统安装包）方案，避免相同内核版本阻止覆盖安装。
- Linux（开源桌面系统）提供对应架构的便携镜像及安装包；macOS（苹果桌面系统）提供未签名通用架构包，当前不承诺应用内自动更新。
- latest.json（更新清单）的平台仅包括当前实际支持的两个微软桌面系统目标和两个开源桌面系统目标，下载地址及签名匹配实际产物。
- 便携包遵循 CC-Switch-Classic-v{classic}-Windows[-arm64]-Portable.zip（含产品版本和可选架构的命名），不要把内核版本代入产品版本位置。
- 核对发布工作流、安装产物、更新清单及用户实际看到的版本；至少验证无更新、发现新版本与完成安装后的再次检查。发版后的问题不能仅靠改文档结案。
