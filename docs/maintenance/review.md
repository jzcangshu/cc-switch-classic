# 内核同步后的代码质量审查指引

本指引用于本项目每次官方内核跟进后的完整审查，也用于普通改动的风险审查。它不依赖指定模型或子代理；单个开发者必须能够完成同样的流程。实施准备见 [上游同步](upstream-sync.md)，产品边界见 [项目契约](project-contract.md)。

## 0. 先确定审查对象与完成条件

使用 [审查报告模板](templates/upstream-review.md)，固定 U0/U1（官方前后提交）与 C0/C1（经典版前后提交），记录工作区是否干净。审查的是合并后的行为及全部受影响消费者，不只是最后一个修复提交。

内核同步以下各节都要执行；普通改动按影响面裁剪并记录理由。纯文档改动可直接进入第 8 节和第 9 节。结论必须由“发现 → 证据 → 修复 → 复验”支撑；模板生成和自动检查不能替代阅读与判断。

## 1. 覆盖官方变更与经典版差异

- 将所有官方变化纳入裁决清单；含新增、删除、重命名、配置和依赖，不只处理发生冲突的文件。
- 对照候选版本与目标官方版本，确认每一项偏离来自经典版契约、必要适配或已记录例外。
- 对改动的属性、命令、翻译键、缓存键、类名和数据钩子查找所有消费者，连同源码断言型测试核对；不要为满足旧测试保留已经无意义的实现。
- 对新增应用和特殊账号卡片检查同一领域的公共分支：过滤结果、空态、排序、分组、可见性、恢复与移除。一个新分支显示正常不代表整个列表逻辑正确。

## 2. 正确性与数据契约

- 沿界面 → 接口封装 → 命令注册 → 服务 → 数据持久化追踪一次真实成功和一次失败路径。
- 覆盖缺失、空、零值、重复、过期、取消、失败后重试、并发切换和关闭窗口；检查请求取消、订阅清理、错误传播和缓存失效。
- 认证与原生配置区分官方账号、第三方密钥及代理接管状态；保留未知字段、用户手工设置与正确的默认模型，失败时可恢复。
- 数据库检查旧版本升级、重复迁移、损坏输入、事务及回滚；协议检查流式事件、错误映射、工具调用、用量与模型名称转换。
- 前后端常量和版本含义由真实生产声明验证，不复制一份测试专用影子常量。

## 3. 可读性、边界与可维护性

- 业务规则放在所属领域，通用组件不逐个识别应用；寻找已有规范实现，避免在大文件继续堆相似分支。
- 删除或收敛已无消费者的参数、复制遗留属性和无效兼容层时确认调用链；重构应减少需要同时理解的状态与概念，不能只是换目录。
- 新增抽象必须解释解决了哪些重复、不变量或边界；不要为了“通用”引入只使用一次的框架。
- 检查类型边界、可选值和静默默认值。宽泛类型或兜底文字如果掩盖缺失状态，应修正模型和初始化来源。
- 文件规模是风险线索，不机械用行数定罪。要求贡献者解释新增职责、依赖方向与更简单的实现。

## 4. 安全、隐私和数据隔离

- 外部配置、会话、协议消息、网址和深链都视为不可信输入；检查路径越界、参数拼接、输出转义、认证边界和日志脱敏。
- 密钥不得进入源码、截图、报告和日志。官方认证保留与第三方路由隔离同时成立，不能只验证其中一种模式。
- 测试目录优先于真实用户目录及兼容回退；环境变量修改和固定端口不能污染另一个测试或正在运行的应用。
- 检查安装、更新、依赖及工作流来源变化；更新终点和签名校验必须保持本项目信任边界。不能为了通过构建关闭校验。

## 5. 性能、资源和并发

检查长会话/大列表、重复请求、分页、缓存失效、频繁重渲染、阻塞操作、无界循环和未释放监听器。拖动或窗口缩放时观察实际帧与布局，不凭代码形式断言性能改进。

重跑通过不能证明首次失败只是负载；必须保留原日志、对照隔离和原并发条件。资源不足时收窄诊断和记录参数，不任意删除断言或放宽超时。

## 6. 界面、语言与平台

- **真实几何**：图表、虚拟列表、弹窗和拖影必须在真实布局环境有非零尺寸；替身保留属性不足以证明最终绘制。检查父容器约束和宽高契约。
- **临界宽度**：至少覆盖宽窗口、布局断点两侧、窄窗口及长文本。额度列、账号组、地址后缀、图标与按钮间距不能互相侵占。
- **同类一致性**：比较新旧账号卡片、图标背景、标题/副标题字号、按钮语义和警示色；相邻分支的细微偏离也会破坏整体。
- **交互可达**：键盘、焦点恢复、触屏、空态、取消与防误操作保护；搜索不能吞掉匹配的特殊账号卡片。
- **四语言**：检查键集合和实际展示；默认回退字符串可能让测试绿灯但只有中文可用。旧文案按真实语义与第三版对照。
- **平台初始化**：平台检测若在模块加载时计算，后续替换函数不会改写常量；分别验证各平台路径，原生窗口操作在桌面验证。
- 按 [项目契约的视觉表](project-contract.md) 逐项留下结果；不要将某个历史宽度或旧测试数量写成固定验收值。

## 7. 经验如何推广为检查方法

| 已核对的历史事实                           | 通用风险                   | 每次如何查                               |
| ------------------------------------------ | -------------------------- | ---------------------------------------- |
| 图表合并时丢失高度，测试替身未暴露         | 测试替身遮蔽真实几何契约   | 跟踪尺寸来源、真实渲染、断言非零边界     |
| 分组翻译仅靠中文回退可用                   | 默认值掩盖缺失资源         | 四语言键集与实际展示双查                 |
| 特殊账号卡被普通列表空态吞掉               | 局部新增没有更新聚合判断   | 穿过过滤、空态、分组和排序全链路         |
| 地址后缀重叠、额度列窄窗溢出、卡片样式偏离 | 单控件正确但组合布局不成立 | 相邻组件、长文本和断点两侧对照           |
| 账号组遗留无用参数和复制属性               | 合并后留下失真接口         | 搜索调用方并收窄真实契约                 |
| 窗口拖动只在另一平台失败                   | 模块级常量绕过测试替换     | 从初始化路径复现平台差异                 |
| 两处产品版本不同步导致循环更新             | 多处真值及口径混用         | 生产常量互验、同版/旧版/新版更新路径验证 |
| 路径过滤缺少历史导致检查被跳过             | 绿状态不等于检查发生       | 核对触发事件、比较基线和具体作业结果     |

前五类经验来自 2026-11-04 的交接材料及本地修复提交 ef352b58（正确性修复）和 626fff1a（界面一致性修复）；后面三类来自原维护文档和实现。提交编号只用于来源追溯，检查方法独立成立，不要求贡献者取得私人分支。历史记录里的严重度和“全量绿”不能原样继承到新候选版本。

## 8. 自动检查与证据

按 [开发与验证](development.md) 运行适用命令。报告逐条填写提交编号、命令、环境、退出码、结果和日志位置；外部报告中的日志只发布脱敏摘要。涉及依赖或打包要验证构建；内核同步必须保留远端持续集成结果和跨平台缺口。

纯文档审查检查：分阶段入口可达、规则不重复/不冲突、命令与代码一致、旧链接已迁移、私人资料与原始交接未进入提交。运行文档检查和差异空白检查；改了维护工具则加跑其专门测试。

自动门禁覆盖入口与链接、维护资料的隐私特征、禁止入库的文件以及维护工具回归。它不能证明任意秘密已经被发现，提交前仍须人工看暂存差异；也不会替审查者作出质量结论。

## 9. 缺陷分级、修复与放行

每个问题记录：严重度、触发条件、影响、具体证据、建议修复、复验结果；无证据的猜测标为待验证。

- P0（紧急）：已确认的数据损坏、凭据泄露、不可恢复的核心故障等，立即阻止交付。
- P1（必须修复）：重要路径或明确项目契约被破坏，合并前修复。
- P2（常规缺陷）：范围受限但成立的问题，修复或由维护者明确接受延期及跟踪方式，不能自行当成无关。
- P3（建议）：可选改进，不以个人审美阻塞整体质量已提升的改动。

不要照搬旧报告将“图表不显示”永远定为紧急；根据本次影响和可恢复性分级。先确认问题，再修复，再审查最终差异。每次修复更新 C1（候选提交）并复验受影响链路；仅当候选未变且不存在新风险时复用先前证据。

只有覆盖完整、必修项关闭、适用检查实际通过、缺口被明确处理，才能给出“通过”；否则写“需修复”或“验证不完整”。最终报告列出未解决事项，不能用空的问题表代替审查。
